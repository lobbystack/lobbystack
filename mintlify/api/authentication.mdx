Every request needs a key. An API key from the dashboard works on one business, and a [platform key](#platform-keys) works on many. Owners and admins create and revoke API keys in the dashboard. API keys, but not platform keys, also connect AI assistants through the [MCP server](/ai/mcp).

## Create a key

<Steps>
  <Step title="Open API keys">
    Go to **Settings** > **API keys**. Only owners and admins see the page.
  </Step>
  <Step title="Name the key and pick its access">
    Use a name you'll recognize later, such as `Zapier`. Select only the scopes the tool needs.
  </Step>
  <Step title="Copy the key">
    LobbyStack shows the full key once. Store it in your tool or a password manager. LobbyStack keeps only a hash, so nobody can show the key again.
  </Step>
</Steps>

Keys look like `lsk_1a2b3c4d_` followed by 32 random characters. The dashboard lists each key by its prefix, `lsk_1a2b3c4d`, with its scopes, who created it, and when it was last used.

## Send the key

Put the key in the `Authorization` header:

```bash
curl https://app.lobbystack.com/api/v1/calls \
  -H "Authorization: Bearer $LOBBYSTACK_API_KEY"
```

A missing, unknown or revoked key returns `401` with the code `unauthorized`.

## Test a key

`GET /me` works with any valid key, whatever its scopes. It returns the key and its business, so an integration can check a connection before it needs a specific scope:

```json
{
  "data": {
    "api_key": {
      "id": "0b7c1d2e-3f40-4a51-8b62-7c83d94ea5b6",
      "name": "Zapier",
      "prefix": "lsk_1a2b3c4d",
      "scopes": ["appointments:read", "appointments:write"],
      "created_at": "2026-09-27T16:58:00.000Z"
    },
    "business": { "id": "75795511-9ee2-4cb2-a89d-f173ec1dd82d", "name": "Maple Salon" }
  }
}
```

## Scopes

Each endpoint except `GET /me` requires one scope. A key without it gets `403` with the code `insufficient_scope`, and the message names the missing scope.

| Scope | Allows |
| --- | --- |
| `business:read` | `GET /business`, `GET /services`, `GET /staff`, `GET /receptionist`, `GET /rules`, `GET /onboarding`, `GET /widget-keys`, `GET /calendars`, `GET /calendars/{connection_id}/calendars`, `GET /notification-preferences` |
| `business:write` | `PATCH /business`, `PATCH /receptionist`, `POST /services`, `PATCH` and `DELETE` on `/services/{service_id}`, `POST /rules`, `PATCH` and `DELETE` on `/rules/{rule_id}`, `POST /rules/reorder`, `PATCH /onboarding`, `POST /onboarding/complete`, `POST /widget-keys`, `PATCH /widget-keys/{widget_key_id}`, `POST /calendars/google/connect`, `PATCH` and `DELETE` on `/calendars/{connection_id}`, `PATCH /notification-preferences` |
| `calls:read` | `GET /calls`, `GET /calls/{call_id}` |
| `contacts:read` | `GET /contacts`, `GET /contacts/{contact_id}` |
| `contacts:write` | `POST /contacts`, `PATCH /contacts/{contact_id}`, `POST /contacts/passcodes`, `POST /contacts/passcodes/generate` |
| `appointments:read` | `GET /appointments`, `GET /appointments/{appointment_id}`, `GET /availability` |
| `appointments:write` | `POST /appointments`, `POST /appointments/{appointment_id}/cancel`, `POST /appointments/{appointment_id}/reschedule` |
| `messages:read` | `GET /messages` |
| `knowledge:read` | `GET /knowledge`, `GET /knowledge/{entry_id}`, `GET /knowledge/sources`, `GET /knowledge/sources/{source_id}` |
| `knowledge:write` | `POST /knowledge`, `PATCH` and `DELETE` on `/knowledge/{entry_id}`, `POST /knowledge/sources`, `PATCH` and `DELETE` on `/knowledge/sources/{source_id}`, `POST /knowledge/sources/{source_id}/expand`, `/retry` and `/cancel`, `POST /knowledge/uploads` and `POST /knowledge/uploads/{upload_id}/complete` |
| `billing:manage` | `GET` and `PATCH /billing`, `POST /billing/checkout`, `GET /billing/checkout/{checkout_id}` and, with a platform key that has access to every business, `POST` and `DELETE /billing/managed-plan` |
| `phone_numbers:manage` | `GET /phone-numbers`, `POST /phone-numbers/search`, `POST /phone-numbers/claims`, `GET /phone-numbers/claims/{claim_id}`, `DELETE /phone-numbers/{phone_number_id}` and `POST /phone-numbers/{phone_number_id}/replace` |
| `team:manage` | `GET /team`, `POST /team/invitations`, `DELETE /team/invitations/{invitation_id}`, `PATCH` and `DELETE` on `/team/members/{membership_id}`, `POST /team/claim-link` |
| `webhooks:manage` | `GET`, `POST`, `PATCH` and `DELETE` on `/webhooks`, and `POST /webhooks/{webhook_id}/test` |

To subscribe an endpoint to an event or change its URL, your key also needs the event's read scope. For example, `call.completed` needs `calls:read`, and the [events table](/api/webhooks#events) lists the rest.

## Platform keys

A platform key (`lsp_...`) onboards and manages many businesses, where an API key works on one. You can use one to set up the businesses you serve, for example with [`lobbystack onboard`](/api/cli). A partner makes its own platform keys in its partner console. The host, whoever runs the deployment, sets the rest in `PLATFORM_API_KEYS`.

### Make a partner's platform key

<Steps>
  <Step title="Open API keys">
    In the [partner console](/white-label/overview), go to **API keys**. Only the partner's owners and admins can make and revoke keys.
  </Step>
  <Step title="Name the key and pick its access">
    Select only the scopes the tool needs. `POST /businesses` needs `businesses:create`, and `POST /users` needs `users:create`.
  </Step>
  <Step title="Copy the key">
    The console shows the full key once. LobbyStack keeps only a hash, so nobody can show the key again.
  </Step>
</Steps>

A partner's key acts as the partner, so it keeps working when the person who made it leaves the team. It reaches the partner's active businesses, including the ones the console created, and no others. It can't start a Polar checkout, set a managed plan or create a claim link. It can't search for or claim phone numbers, or read or change alert preferences, because those act as a person.

`POST /businesses` with a partner's key creates a business of the partner, with no owner yet. Name the owner in `owner_email`, and the partner emails them an invitation to sign in on its dashboard. `access_level` sets what the business's own team can use: `full`, the default, or `activity`. A partner's platform keys can create 30 businesses an hour between them. The invitations it sends through `POST /team/invitations` and `POST /users` come from the partner and link to its dashboard.

The links the API returns for a partner's business, such as a widget's script tag or a calendar connect link, point at the partner's dashboard too.

### Make a host's key

The dashboard has no page for the host's keys. On a self-hosted deployment, `pnpm platform-key:create` writes a new key to `.platform-keys/<prefix>.json` and prints its entry for [`PLATFORM_API_KEYS`](/self-hosting/environment-variables). Each entry sets:

- The group the key belongs to (`group`; pass `--group`). Keys in the same group reach the same businesses.
- The verified LobbyStack account the key acts as (`owner_email`), which owns the businesses the key creates.
- Whether the key reaches every business (`"access": "all"`; pass `--access all`) or, by default, only the ones its group's keys onboarded (`"access": "group"`).
- Its scopes. Unless you name some, a new key gets the scopes an API key can hold. `POST /businesses` needs `businesses:create` and `POST /users` needs `users:create`. Only platform keys can hold these two, and a new key gets them only when you pass `--create-businesses` or `--create-users`. `GET /businesses` needs `business:read`.

Older entries call the group `partner` and may set `"access": "partner"`. Both still work, and the key reaches the same businesses. To update one, change `partner` to `group` and `"access": "partner"` to `"access": "group"`. Update the admin first: older versions refuse `group`. The admin refuses an entry that sets both `partner` and `group`, and with it every key in `PLATFORM_API_KEYS`.

<Warning>
A key with `"access": "all"` acts as its `owner_email` account on every business on the deployment, without being on any team, and can read and change all of them. That key, and that account with its password, sessions and email inbox, are root credentials. Give them to as few people as you can, keep the account's password as safe as the database's, and remove the key's entry from `PLATFORM_API_KEYS` if either leaks. `pnpm platform-key:create --access all` prints the same warning.
</Warning>

Once the admin restarts without a key's entry in `PLATFORM_API_KEYS`, requests with that key fail, and LobbyStack turns off the webhook endpoints the key created. To keep one, turn it back on with another of your platform keys.

### Use a platform key

`POST /businesses` creates a business. `GET /businesses` lists the ones the key's group onboarded, or for a partner's key, every business of the partner. Every other request names its business in the `LobbyStack-Business` header:

```bash
curl https://app.lobbystack.com/api/v1/services \
  -H "Authorization: Bearer $LOBBYSTACK_PLATFORM_KEY" \
  -H "LobbyStack-Business: 75795511-9ee2-4cb2-a89d-f173ec1dd82d"
```

Without the header, the request returns `400` with the code `business_required`. A business the key can't reach returns `404`. `GET /me` works without the header and shows the key's group and reach in `platform`. `platform.reach` is `group` for a key with group access and `all` for a key that reaches every business. API v1 keeps the older names as well: `platform.partner` repeats `platform.group`, and `platform.access` repeats `platform.reach` but reads `partner` for group access. For a partner's key, `platform.partner_id` names the partner, which is also the key's group. It's `null` for the host's keys.

`POST /team/claim-link` hands a business to its owner. Once they accept, a key with group access no longer reaches it, and a key with access to every business still does. Either way, `GET /businesses` stops listing it. LobbyStack also turns off the business's webhook endpoints that a platform key, the account that sent the link, or that account's API keys created. A partner's business stays with the partner, so `POST /team/claim-link` returns `409` for one. Only the partner can release it to its owner.

Only a verified LobbyStack account can accept a claim link, and the link's page lets an owner without an account sign up first. To invite them ahead of it, `POST /users` emails the address a sign-up link, or a sign-in link if the address already has an account. It never makes an account, so the owner signs up with their own password or with Google, and it answers the same either way, so you can't tell who has an account. A platform key can invite 50 addresses a day.

## Revoke a key

On **Settings** > **API keys**, click **Revoke** next to the key. Requests with it fail right away, and you can't undo it. Create a new key if you still need access.

LobbyStack also turns off the webhook endpoints the key created. To keep one, turn it back on from the **Webhooks** card in **Integrations**.

To revoke a partner's platform key, click **Revoke** next to it on the partner console's **API keys** page. Requests with it fail right away. LobbyStack turns off the webhook endpoints the key created on every business, and revokes the team invitations the key sent that nobody has accepted. Owners the key invited when it created their business can still accept.

## Rate limits

Each key can make 120 requests per minute. Self-hosted deployments can change this with `PUBLIC_API_RATE_LIMIT_PER_MINUTE`. The window resets at the start of each minute.

Every response carries these headers:

| Header | Meaning |
| --- | --- |
| `X-RateLimit-Limit` | Requests allowed per minute. |
| `X-RateLimit-Remaining` | Requests left in the current minute. |
| `X-RateLimit-Reset` | Unix time, in seconds, when the window resets. |

Past the limit, the API returns `429` with the code `rate_limited` and a `Retry-After` header with the seconds to wait.

## Keep keys safe

- Use one key per tool so you can revoke one without breaking the others.
- Give each key the fewest scopes that work.
- Never put a key in browser code or a mobile app. Call the API from a server.
- LobbyStack logs each request with the key's ID, never the key itself, and records changes made with a key in the business's audit log.
